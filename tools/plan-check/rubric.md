# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| grounded-diagnosis | The plan's stated cause, read against every step, control run, and artifact in the repro evidence block (and any maintainer finding in the thread highlights). | Pass if the stated cause explains the reproduced behavior AND nothing in the repro evidence rules it out. Fail if any control run, step, or artifact in the package shows the blamed component working correctly, or shows the failure happening before or without the blamed component (e.g. the control passes through the same code; the data is already wrong before the step the plan blames). Fail if the plan names no cause at all. A cause copied from the thread still fails if the package's own evidence contradicts it. | required |
| bounded-scope | The plan's change list, in-scope / not-in-scope lines, and approach steps, read against what the issue asks for. | Pass if every planned change is needed to fix the reproduced bug (plus its regression test); an explicit deferral of bigger work to a follow-up passes. Fail if the plan also commits to work the issue does not need: refactors or rewrites, dependency/library migrations or upgrades, new options/settings/UI, new frameworks, CI changes, or fixes to other features "while in the area", even if the core fix inside it is correct. | required |
| executable-approach | The plan's approach: named files, functions, or code sites, and the chosen change. | Pass if a stranger could start the edit without asking the author anything: at least one concrete file, function, or code site is named AND one specific change is chosen. Fail if the location is "somewhere", the layer is undecided ("X or Y, whichever is easier", "not sure"), the work is "investigate/profile first", or key decisions are deferred to build time. | required |
| decisive-test | The plan's test plan, read against the repro evidence's steps and its Expected line. | Pass if the test re-runs the repro (or an equivalent regression test through the real code) AND names a specific observable outcome that differs from the current failure (an exit code, output, color, assertion passing, timing number). Fail if the only check is "run the full test suite", "should feel fast/normal", "nothing else breaks", or any outcome that would look the same before and after the fix. | required |
| honest-unknowns | The plan's risks/unknowns section and any hedged claims. | Pass if real uncertainties are named as open (or the change is small enough that none is material). Fail only if the plan presents something the package shows is unknown or untested as settled fact. | preferred |
| thread-and-convention | The plan comment, read against (a) every maintainer/owner comment in the thread highlights and (b) the repo-facts contribution policy, especially any AI-use policy. | Fail if a maintainer or owner in the thread gave explicit direction (a culprit location, a preferred approach, a rejected approach, a patch or build to test) and the plan or comment ignores or contradicts it without engaging it by name. Fail if the repo-facts policy requires AI-use disclosure and the comment contains no disclosure stating the tool and extent of AI help (treat every package as AI-assisted work). Otherwise pass: a thread with no maintainer direction and a repo with no disclosure requirement passes this check. | required |

## Verdict rule

Accept (ready) only if all five required checks pass: grounded-diagnosis, bounded-scope, executable-approach, decisive-test, and thread-and-convention. Any required check that fails means reject (hold). An `unclear` (`?`) on a required check counts as a fail, because a plan that cannot be verified from the package is not ready to build from. The preferred check (honest-unknowns) is reported but never changes the verdict, whether it passes, fails, or is unclear.
